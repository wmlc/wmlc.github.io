加锁代码

 use Illuminate\Support\Facades\DB;

try{
  DB::transaction(function () use ($data) {
    # 获取用户信息，加悲观锁，其他的不可读写
    $userInfo = UserProfile::query()->where(['uid' => $data['apprentice_uid']])->lockForUpdate()->first(); 

    # 第一个sql操作
    User::query()->where(['id' => 1])->increment('exchange_coupon', 10);

    throw new \Exception('异常，回退');

    # 第二个sql操作
    $TradeHistory = new TradeHistory();
    $TradeHistory->is_pay = Config::$TRUE;
    $TradeHistory->save();

    # 第三个sql操作
    $Apprentice = new Apprentice();
    $Apprentice->is_send = $data['is_send'];
    $Apprentice->save();
    return true;
  });
}catch (\Throwable $ex){
  return false;
}

注意事项

一种说法解读

lockForUpdate() 只会对存在的记录行加排它锁（X 锁）。

如果你查不到记录，MySQL 根本不知道你要锁哪一行，只能靠后续 insert 加意图锁来解决冲突。

但如果多个事务都查不到这条记录，都去插入，就变成了“同时加锁”，产生了死锁。

> 所以：悲观锁只对已存在的记录有效，对不存在的记录无能为力。

这个说法不完全正确，存在两个关键误解。

❌ 误解一："查不到记录就只靠 INSERT 的意图锁解决冲突"

这取决于 事务隔离级别：

隔离级别 SELECT ... FOR UPDATE 查不到数据时的行为
REPEATABLE READ（InnoDB 默认） 对查询条件对应的间隙（Gap）加排他锁（X Gap Lock），阻止其他事务在该范围内 INSERT
READ COMMITTED 确实不加间隙锁，仅持有短暂的意向锁，释放后其他事务可并发 INSERT

在 MySQL 默认的 REPEATABLE READ 下，即使查不到行，InnoDB 也会加锁，而且加的是能阻止 INSERT 的间隙锁/Next-Key Lock。这正是我之前说"不会重复插入"的依据。

📖 MySQL 官方文档明确说明：
"If you have no records matching the WHERE clause and InnoDB is using REPEATABLE READ isolation level, InnoDB locks the index range searched."

⚠️ 误解二："多个事务都查不到 → 同时加锁 → 死锁"

实际发生的是阻塞（Blocking），而非死锁（Deadlock）：

  1. 事务 A 执行 SELECT ... FOR UPDATE → 未命中 → 获得间隙 X 锁
  2. 事务 B 执行相同查询 → 被间隙锁阻塞，进入等待状态（不是"同时加锁"）
  3. 事务 A 执行 INSERT → 成功 → COMMIT → 释放间隙锁
  4. 事务 B 解除阻塞 → 重新扫描 → 此时能看到事务 A 插入的行 → 走更新分支

这是一个严格的串行化过程，不存在循环等待，因此不会死锁。

真正会死锁的场景

只有当两个事务以不同顺序访问资源时才会死锁，例如：

  • 事务 A：锁定 (room_id=1) 的间隙 → 尝试插入 (room_id=2)
  • 事务 B：锁定 (room_id=2) 的间隙 → 尝试插入 (room_id=1)

相同条件的并发 SELECT FOR UPDATE + INSERT 不构成死锁条件。

✅ 修正后的准确表述

  • 在 REPEATABLE READ（默认）下：lockForUpdate() 对不存在的记录有效，通过间隙锁阻止并发 INSERT，不会重复也不会死锁。
  • 在 READ COMMITTED 下：lockForUpdate() 对不存在的记录无效，多个事务可能并发查到空结果并各自 INSERT，导致重复数据（但通常也不是死锁，而是违反唯一约束报错）。
  • "悲观锁对不存在的记录无能为力" 这个结论仅在 READ COMMITTED 下成立，不能作为通用结论。

📌 实践建议

如果你无法确认生产环境的隔离级别是否被修改过，最稳妥的做法仍然是：添加唯一索引作为兜底 + 使用 ON DUPLICATE KEY UPDATE value = value + ? 原子操作。这样无论隔离级别如何，都不会产生重复数据。
