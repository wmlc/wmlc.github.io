从编码原理讲起：为什么 gRPC、微服务、游戏通信都选了它

如果你看过 gRPC、微服务网关或者手游的通信协议，会发现它们几乎清一色用 Protocol Buffers（简称 Protobuf），而不是我们更熟悉的 JSON 或 XML。官方说法永远是那两个字：性能。

但性能到底好在哪？这篇文章不堆 benchmark 截图，而是从编码原理层面把这件事讲透。

TL;DR · 核心结论

JSON / XML 是文本协议，Protobuf 是二进制协议 —— 这是一切性能差异的根源。

文本协议把 schema（字段名、类型）内嵌在每一条数据里，换来可读性；Protobuf 把 schema 抽到编译期，数据里只剩纯粹的值，换来体积和速度。

一、先看差距：同一份数据的三种写法

Protobuf 不需要传输字段名

假设要传输一个用户对象：id=300, name="Tom", email="tom@abc.com", admin=true。

XML（≈ 83 字节）

<user>
  <id>300</id>
  <name>Tom</name>
  <email>tom@abc.com</email>
  <admin>true</admin>
</user>

JSON（≈ 60 字节）

{"id":300,"name":"Tom","email":"tom@abc.com","admin":true}

Protobuf（仅 23 字节，二进制以 hex 展示）

08 AC 02  12 03 54 6F 6D  1A 0B 74 6F 6D 40 61 62 63 2E 63 6F 6D  20 01
└ id=300   └ "Tom"        └ "tom@abc.com"               └ admin=true

字段名越长、数字越多、嵌套越深，差距会被进一步拉大，实际业务中 3~10 倍很常见。

二、根源 1：二进制编码 vs 文本编码

这是最本质的差异。JSON / XML 里的一切都是字符，而字符是给人看的，不是给机器存的。

  • 数字 300 在 JSON 里是 3 个字符 '3' '0' '0'，占 3 字节；接收方还要做一遍「字符串 → 整数」的转换。Protobuf 直接按二进制存，只要 2 字节，读出来就是整数，零转换。

  • 布尔值 true 在 JSON 里占 4 字节，在 XML 里连同标签占 18 字节；Protobuf 只要 1 字节。

  • JSON 里到处是为人类服务的装饰：引号、冒号、逗号、大括号；XML 更夸张，每个字段的标签名要原样写两遍（开标签 + 闭标签）。

文本编码有双重开销：存储上冗余，解析上耗时。 Protobuf 把这两笔开销都省掉了。

三、根源 2：Varint 变长整数编码

Protobuf 的整数不是定长存储，而是用 Varint（变长整数）编码：每个字节的最高位是「继续位」，剩下 7 位存数据；小数值只用 1~2 个字节。

另外，负数会用 ZigZag 编码（sint32 / sint64）先把负数映射成小正数，再走 Varint，避免负数被编码成 10 个字节的灾难。

四、根源 3：用字段编号代替字段名

看一条 JSON：{"email":"tom@abc.com"} —— 键名 "email" 加引号冒号共 8 字节，键名常常比值本身还长，而且每条数据都原样重复一遍。

Protobuf 的做法是：schema 在 .proto 文件里定义一次，编译期双方都知道；线上传输的数据里只有字段编号（一个整数），完全没有字段名。

message User {
  int32  id    = 1;   // 传输时只带编号 1，不带 "id"
  string name  = 2;
  string email = 3;
  bool   admin = 4;
}

没有任何引号、冒号、逗号、闭标签，也没有任何字段名 —— 数据里只剩纯粹的值。

五、根源 4：解析方式的代差

体积小省的是带宽，解析快省的是 CPU。两者的解析过程完全是两个时代：

文本协议的解析（JSON / XML）

  • 逐字符扫描的状态机：找引号、找冒号、处理转义字符 \n \" \\
  • 键名是字符串，要做字符串比较才能知道是哪个字段
  • 数字要做字符串 → 数值转换
  • 大量临时字符串对象 → 内存分配 + GC 压力

Protobuf 的解析

  • 读 1 个 tag 字节 → 位移运算得到字段编号和类型 → 按类型定长直读或按长度切片
  • 字段编号是整数，switch 一下就定位到生成代码里的字段，无字符串比较、无反射
  • 遇到不关心的字段，根据类型直接算出长度跳过去（skip），连对象都不构造
  • 进阶实现可做到零拷贝：直接引用字节缓冲区，不复制数据

一句话：文本解析是「运行时解释」，Protobuf 是「编译期确定 + 位移直读」。 protoc 编译器会根据 .proto 生成强类型的序列化 / 反序列化代码，解析路径在编译时就固定死了，运行期没有任何「猜测」。

六、数据说话

维度 XML JSON Protobuf
编码形式 文本 文本 二进制
体积（同一份数据） 基准的 2~4 倍 基准 约为 JSON 的 1/3 ~ 1/10
序列化速度 最慢 基准 快约 5 ~ 20 倍
反序列化速度 最慢 基准 快约 5 ~ 100 倍
schema 内嵌 / 可选 DTD 内嵌在每条数据里 编译期确定，数据不带
可读性 / 调试 高 高 几乎不可读，需工具解码

注：具体倍数随语言实现、数据结构而不同，上表是公开 benchmark 中常见的数量级，用于建立直觉。

七、不是没有代价

客观地说，Protobuf 的性能是用这些换来的：

  • 不可读：抓包看到的是一堆 hex，排查问题要靠 protoc --decode 或专用工具。
  • 强依赖 schema：收发双方必须持有同一份 .proto 定义，字段变更要管理编号兼容性。
  • 前端不友好：浏览器原生不认识 Protobuf，Web 场景还是 JSON 更顺手。
  • 小数据量优势不明显：几十字节的消息，省下的开销可以忽略。

八、到底怎么选

  • 微服务内部调用、gRPC、高频通信、移动端省流量 → Protobuf
  • 对外开放 API、需要人直接阅读、快速联调 → JSON
  • 遗留的企业系统对接、文档型数据 → XML（基本只剩这些场景）

一句话总结

JSON / XML 把 schema 内嵌在每一条数据里，用文本描述一切，换来的是可读性；Protobuf 把 schema 抽到编译期，用二进制描述数据，换来的是体积和速度。

性能差异的本质，是「运行时解释」与「编译期确定」的差异。
