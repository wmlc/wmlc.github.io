从工作原理到 description 调优，一篇讲透 Skill 的编写、触发与调试

不知道你有没有遇到过这种情况：让 AI 处理一份 PDF，它回你一段「我帮你分析一下」的文字，但既不调用工具，也不生成文件 —— 因为它不知道你的环境里有什么库、文件放在哪、输出要什么格式。

Skills（技能包）就是为解决这个问题而生的。这篇文章系统梳理了 Skills 的核心概念、工作原理、编写规范和调试方法，是我近期实践的一份完整笔记。

TL;DR · 核心结论

Skill 不是提示词，而是一套完整的软件能力包。Prompt 解决一次问题，Skill 把能力沉淀成资产。

写好一个 Skill 的关键不在指令正文，而在 description —— 它是 AI 决定是否启用这个技能的唯一依据。

一、Skills 到底是什么

Skills 是一个开放格式，用于为 AI 智能体（Agent）添加专业技能和知识。三个概念先对齐：

概念 定义
AI 智能体 大模型 + 动手做事的能力（能感知、推理、行动）
Skills 告诉智能体「如何完成某类任务」的说明书（一个 SKILL.md 文件）
本质 人类编写的领域知识 / 流程 / 约束 → AI 读取后自动执行

💡 一个精准的比喻：智能体 = 聪明的新员工；Skill = 公司的 SOP 手册。
类比软件世界：Agent 是操作系统，Skill 是应用程序 —— PDF 分析、网页抓取、SQL 优化、数据统计，每个 Skill 都是独立的能力单元。

聊天机器人 vs 智能体

聊天机器人 智能体
能力 只能说（基于训练数据猜测） 能听懂 + 思考 + 动手干
示例 「北京大概晴天 25 度」 调接口返回真实天气数据
局限 无法访问外部系统 可查数据库、订票、生成文件

智能体的工作流程是「三步走」：听懂需求（大模型理解）→ 决策选技能（大模型判断用哪个 Skill）→ 执行并返回结果（靠 Skills 完成）。

Skills 带来的三大核心价值：

  1. 从会聊天到会干活：让 AI 成为真正的任务执行者（比如直接输出可用的 .docx 文件）；
  2. 可复用的经验包：一次编写，所有人、所有调用的结果稳定一致；
  3. 人机协作的桥梁：人类定义「怎么做」，AI 负责「去做」。

二、定位：Skills vs Prompt vs MCP

很多人分不清这三者的边界，一张表说清楚：

维度 Prompt Skills MCP
定位 一次性口头交代 知识复用（经验/流程/最佳实践） 能力扩展（连接 API/数据库/工具）
载体 对话文本 Markdown 文件，人人可写 需编码 + 服务器配置
加载方式 每次手动输入 渐进式加载，Token 效率高 启动时全量加载，Token 消耗高
复杂度 极低 低，无需后端 高，集成能力强

一句话区分：Skills 管「知道怎么做」，MCP 管「能连上什么」。 二者互补而非替代 —— 比如用 MCP 连上数据库，再用 Skill 规定「查数 → 清洗 → 出报表」的标准流程。

Skills 的典型适用场景：领域专业知识封装（法律审查、代码规范等）、多步骤工作流程固化、公司规范/模板标准化、特定工具使用方法封装。

三、工作原理：渐进式披露

智能体靠读文件理解 Skill。读完 SKILL.md 后它搞清楚三件事：能干什么（能力描述）、需要提供什么（输入参数）、有什么规矩（环境约束和注意事项）。

核心设计思想是渐进式披露（Progressive Disclosure）：分阶段加载不同详细程度的信息，避免一次性耗尽上下文空间。

阶段 加载内容 典型大小 作用
① 发现（Discovery） name + description ~100 tokens 判断是否与当前任务相关
② 激活（Activation） 完整 SKILL.md ≤5000 tokens 读取完整指令
③ 执行（Execution） 脚本、参考资料等 按需加载 实际调用工具完成任务

优势：可同时挂载大量技能而 Token 消耗极低 —— 先读 description，命中后才加载完整内容。

一次完整的 Skill 执行是一个 8 步闭环：

接收请求 → 理解意图 → 制定计划 → 选择 Skill → 执行 → 获取结果 → 生成回复 → 返回用户

执行路径是受控的：命中 Skill → 加载 SKILL.md → 建立工具权限与行为边界 → 推理 → 只在确实需要时才调用被允许的工具，否则在规则内完成逻辑。

Agent 负责接收请求、思考和决策，Skill 负责执行动作。 SKILL.md 就是连接两者的「操作手册」—— 注意，Skill 本身不决定何时被使用，决策权在 Agent。

四、解剖一个 Skill

一个 Skill = 一个文件夹 + 一个 SKILL.md。标准目录结构：

my-skill/
├── SKILL.md          ← 核心执行文件（最重要，必须）
├── metadata.json     ← 元信息（机器可读，可选）
├── scripts/          ← 可执行脚本（不加载到上下文）
├── references/       ← 详细参考文档
├── assets/           ← 模板、图片等静态资源
├── examples/         ← 示例（Few-shot）
├── resources/        ← 资源（配置/模板）
├── tests/            ← 测试
└── README.md         ← 使用说明

目录化背后的原则是避免上下文膨胀：核心规则放 SKILL.md，详细资料放 references/，实用逻辑放 scripts/（执行但不加载）。这也解决了单文件方案的老问题：无法维护、无法测试、无法复用、无法版本管理、无法多人协作。

各文件的分工：

文件/目录 作用 关键点
SKILL.md 定义执行逻辑 必须包含：功能说明 / 何时使用 / 何时不用 / 输入 / 指令 / 输出
metadata.json 结构化元信息 description 字段最重要（Agent 靠它匹配）
examples/ Few-shot 示例 比堆提示词更有效，规范输出格式
scripts/ 真正执行代码 读 PDF、OCR、调数据库等实际工作
resources/ 配置与代码分离 prompt 模板、config.yaml、SQL 模板等
tests/ 验证效果 回归测试、A/B 测试、自动评估

SKILL.md 的两大部分

┌─────────────────────────────┐
│ ① YAML Frontmatter（元数据）  │  ← 告诉 AI「我是谁、何时用我」
├─────────────────────────────┤
│ ② Markdown 指令区域           │  ← 告诉 AI「具体怎么做」
└─────────────────────────────┘

Frontmatter 字段一览：

字段 必填 限制 说明
name ✅ ≤64 字符，仅小写字母/数字/-，不能以 - 开头结尾，须与父目录名一致 唯一标识符，kebab-case
description ✅ ≤1024 字符 最重要，决定何时触发
license ❌ — 许可证（如 Apache-2.0）
compatibility ❌ ≤500 字符 环境/依赖说明
metadata ❌ — 自定义键值对（作者、版本等）
allowed-tools ❌ 空格分隔 允许的工具列表（实验性）

命名推荐动名词形式（动词 + -ing），一眼看清能力：processing-pdfs、analyzing-spreadsheets、code-reviewer、sql-optimizer。反面教材：helper（太模糊）、MySkill（大写违规）、sql_optimizer（下划线不是约定）、deploy-check-tool-v2（版本信息应放文件内部）。

⚠️ 关键限制：指令区域建议 ≤ 500 行 / ≤ 5000 tokens。技能激活后整个 SKILL.md 会被加载进上下文，过长就是纯浪费 —— 超出部分移到 references/ 单独存放。

一个可直接套用的完整模板：

---
name: pdf-processing
description: 从PDF提取文本和表格，填写表单，合并PDF。用户提及PDF处理时使用。
license: Apache-2.0
compatibility: Requires Python 3.10+
metadata:
  author: your-name
  version: "1.0"
---

# PDF 处理技能

## 操作步骤
1. 第一步：...
2. 第二步：...

## 示例
### 输入 / 输出
...

## 注意事项
- ...

⚠️ 反模式提醒：指令只写「读取 PDF → 总结 → 返回」这种一句话流程，缺少场景界定和输出格式 —— 这是新手最常见的错误。

五、description：决定生死的那几行字

这是整篇我最想划重点的部分。回顾三层加载机制：发现阶段 Agent 只能看到每个技能的 name + description，正文完全不参与触发判断。也就是说 ——

description 是 Agent 判断是否激活技能的唯一依据。 写得差 → 误报 / 漏报 / 激活错误技能。而且 Skill 不是被用户「调用」的，是 AI 自主决定是否使用的，你没有任何手动兜底的机会。

写法公式：description = 功能说明 + 触发条件 + 关键词

description: 从 PDF 文件中提取文本和表格，填写 PDF 表单，合并多个 PDF。处理 PDF 文档或用户提及 PDF、表单或文档提取时使用。
#            ↑ 功能说明（做什么）                              ↑ 触发条件（什么时候用）

四个编写技巧

  1. 包含具体触发关键词：列出用户可能说的词，如「PDF」「提取」「表单」；
  2. 具体而非笼统：❌「帮助处理各种文件」→ ✅「处理图像文件，调整大小、转换格式、应用滤镜」；
  3. 列出多个使用场景：帮助 Agent 匹配同一意图的不同表述；
  4. 区分相似技能：多个相关 Skill 的描述必须有明显差异。

长度控制：简单技能 50–100 字符，中等 100–200，复杂 200–400。上限 1024 字符，但不是越长越好 —— 过长反而干扰判断。

三种实用的触发策略

# 策略一：列举具体场景（功能 + 何时用）
description: >
  处理 Excel 和 CSV 文件，包括：读取、清洗、生成图表、
  计算统计、合并表格。当用户提到 Excel、xlsx、CSV、
  表格数据、数据清洗、财务报表时，应优先使用此 Skill。

# 策略二：使用"推动性"语言（对付漏报）
description: >
  生成专业 PPT。当用户需要制作幻灯片、演讲稿、汇报材料时，
  必须使用此 Skill，即使用户没有明确说"用 pptx 格式"。

# 策略三：直接列出触发关键词
description: >
  代码审查助手，分析代码质量、发现 Bug、给出改进建议。
  关键词：code review、代码审查、bug 检查、重构建议、静态分析。

什么任务会触发，什么不会

请求类型 示例 触发？ 原因
简单单步 「读取这个 PDF」 ❌ 通常不触发 AI 直接处理更高效
复杂多步 「提取表格并转 Excel」 ✅ 触发 需要专门工作流
专业领域 「合并 PDF 并加水印」 ✅ 触发 涉及特定工具链
明确格式要求 「生成公司模板的 Word 报告」 ✅ 触发 需要格式规范

多个 Skill 同时匹配时，Agent 选最相关的一个。冲突的解法：让 description 有排他性 —— 比如两个 PDF 技能，一个明确写「PDF 创建」，一个明确写「PDF 读取」；功能太相似的就干脆合并，内部分支处理。记住：「能做什么」≠「应该什么时候用」。

三大常见问题速查

问题 原因 解法
总是被激活 描述太宽泛 加限定条件和使用场景
从未被激活 缺少用户常用关键词 补充更多触发词
激活了错误技能 多个 Skill 描述太相似 让描述更具区分度

一个真实的 description 优化演进过程：

# v1 - ❌ 漏报风险极高：没有场景、没有关键词
description: 提取 PDF 文本。

# v2 - ⚠️ 有场景了，但触发词覆盖仍不够
description: 从 PDF 文件中提取文本内容和表格数据。使用场景：提取 PDF 文字、读取 PDF 内容、PDF 转文本。

# v3 - ✅ 功能 + 场景 + 关键词三要素齐备
description: 从 PDF 文件中提取文本内容和表格数据。使用场景：提取 PDF 文字、读取 PDF 内容、PDF 转文本、用户提及「PDF 提取」「读取 PDF」「PDF 文字」「PDF 内容」等关键词时使用。

调优不必纯靠猜：官方的 skill-creator 提供了触发评估脚本，可以自动跑「测试 → 打分 → 改 description → 再测」的循环：

python -m scripts.run_loop \
  --eval-set evals/trigger-eval.json \
  --skill-path my-skill/ \
  --max-iterations 5 \
  --verbose

六、工程化：脚本扩展与参数传递

什么时候该写脚本

判断信号很明确：当 Agent 多次重复实现相同逻辑时，就该把它固化成脚本了。脚本封装复杂逻辑、提供经过测试的可靠实现，也避免 SKILL.md 里堆代码。

两种使用方式：简单场景用一次性命令（uvx ruff@0.8.0 check .、npx eslint@9 --fix .，注意固定版本号保证行为一致）；需要复用的复杂逻辑才放进 scripts/。脚本编写三原则：自包含（声明依赖）、清晰错误处理（错误输出到 stderr，含具体原因和用法提示）、处理边界（验证输入，优雅拒绝而非崩溃）。

为 Agent 设计脚本的 8 个要点（重点⭐）

要点 说明
禁止交互式提示 Agent 在非交互 Shell 运行，所有输入通过参数 / 环境变量 / stdin 传入
提供 --help 这是 Agent 了解脚本接口的主要方式，含说明 + 参数 + 示例
有用的错误信息 越具体，Agent 越容易自我纠正（指明「期望值 vs 实际值」）
结构化输出 优先 JSON / CSV；数据 → stdout，诊断 → stderr
幂等性 Agent 可能重试，「不存在则创建」比「重复报错」安全
Dry-run 支持 破坏性操作提供 --dry-run 预览
有意义退出码 不同失败类型用不同退出码
安全默认值 破坏性操作需 --confirm / --force 明确确认

在 SKILL.md 中用相对于 Skill 根目录的路径引用脚本（Agent 会自动解析），先列清单再在步骤中引用：

## 可用脚本
- **scripts/validate.sh** — 验证配置文件
- **scripts/process.py** — 处理输入数据

## 操作流程
1. 运行验证：bash scripts/validate.sh "$INPUT_FILE"
2. 处理数据：python3 scripts/process.py --input results.json

依赖分发三级策略：SKILL.md 中文字说明（最简单）→ 虚拟环境（复杂项目）→ Docker（完整运行环境）。编写前务必了解目标用户的运行环境，Python 是最安全的选择。

参数传递：没有函数签名，上下文就是参数

Skills 没有传统函数式的显式参数，而是通过对话上下文感知输入。参数来源有四种：用户当前消息（最直接）、上传的文件（通过路径传入）、历史对话（上下文中引用）、系统变量（当前日期、工作目录等）。

做法是在 SKILL.md 里用自然语言声明「输入要求」—— 这段话其实是写给 AI 自己看的，它据此从上下文提取信息，缺信息时主动追问用户：

## 输入要求
用户应提供以下信息（从对话上下文中获取）：
- **文件路径**：已上传 CSV 文件的路径
- **分析目标**（可选）：如 "找出空值"、"统计分布"
- **输出格式**（可选）：表格、图表或文字摘要

若上述信息未明确，主动向用户确认后再执行。

脚本侧则用标准的 argparse 接收，执行前必须做参数验证（路径是否提供、文件是否存在、扩展名是否正确、大小是否合理）。始终使用绝对路径，访问前先 os.path.exists() 检查；错误信息要清晰说明「期望什么 + 实际得到什么」，方便 Agent 向用户反馈。

整体链路：SKILL.md 声明「要什么」→ Agent 从上下文提取 → 脚本用 argparse 接收 → 执行前验证。

七、调试：三类问题，逐层排查

Skill 出问题无非三种，排查顺序有讲究：

问题类型 现象 优先排查点
① 未触发 AI 完全没使用 Skill description 写法、任务复杂度
② 触发但执行错误 Skill 被读取，脚本运行失败 脚本路径、依赖、参数格式
③ 触发但结果不对 输出与期望有出入 SKILL.md 指令清晰度

问题一：未触发（三步排查）

  1. 确认文件被加载：目录结构正确、SKILL.md 存在且非空；
  2. 检查 YAML frontmatter 格式：必须以 --- 开始和结束；字段名无多余空格；冒号后必须有一个空格；
  3. 换更复杂的测试提示词：「分析这个文件」太简单不易触发，改成「分析这份销售数据 CSV，找出月度增长趋势，生成统计摘要表格」。

问题二：脚本执行错误（速查表）

错误信息 原因 修复
ModuleNotFoundError 依赖未安装 安装对应包（注意目标环境的包管理方式）
FileNotFoundError 文件路径错误 确认文件实际位置，使用绝对路径
PermissionError 无写入权限 输出目标改到有权限的目录
SyntaxError 脚本语法错误 用 python -m py_compile 脚本.py 检查

快速语法自检：python -m py_compile scripts/process.py（Python）或 bash -n scripts/run.sh（Shell）。脚本内调试可在关键节点加 print(f"[DEBUG] ...")，但调试完成后务必删除，避免污染正式输出。

问题三：结果不符合预期

根因几乎总是 SKILL.md 指令含糊或有歧义。感受一下写法差距：

❌ 含糊 ✅ 清晰
「处理完成后输出结果」 「将结果保存到输出目录，并在对话中展示文件路径」
「分析数据」 「计算各列均值、中位数、标准差，以 Markdown 表格输出」
「生成报告」 「生成含摘要、数据表格、结论的 HTML 文件，保存到输出目录」

排查时可以在 SKILL.md 中临时加一段「调试模式」指令：执行前先输出识别到的输入路径、期望的输出格式、计划步骤列表，等确认后再继续 —— 定位完问题记得删掉。

💡 调试核心思路：先确认触发 → 再确认执行 → 最后确认输出，逐层缩小范围。

八、上手路径：创建你的第一个 Skill

Skills 通常有两个存放位置：个人全局目录（跨项目可用）和项目目录（团队共享）。以 Claude Code 为例，路径分别是 ~/.claude/skills/ 和 项目目录/.claude/skills/，其他平台约定类似。

创建一个「Python 命名规范」技能，只需两步：

# 1. 创建 Skill 目录
mkdir -p .claude/skills/python-naming-standard

# 2. 编写 SKILL.md
---
name: python-naming-standard
description: 当用户要求重构、审查或编写 Python 代码时，请参考此规范。
---

## 指令
1. 所有内部辅助函数必须以 `_internal_` 前缀命名
2. 发现不符合规则的代码，自动提出修改建议
3. 执行提交前必须检查此规范

## 参考示例
- ✅ `def _internal_calculate_risk():`
- ❌ `def _calculate_risk():`

之后启动 Agent 输入任务（如「帮我写一个计算折扣的函数」），它会自动匹配这个 Skill 并按规范生成代码。调用零门槛：自然语言即可，AI 自动路由到对应 Skill。

站在生态的肩膀上

Skills 生态已经相当成熟，优先复用而非从零编写：

资源 说明
Anthropic 官方仓库 github.com/anthropics/skills，覆盖设计、开发、办公、文档编辑，多数开源
Skill 聚合入口 skills.sh / skillsmp.com（中文）/ agentskills.io（标准站点）
Awesome 精选 github.com/ComposioHQ/awesome-claude-skills
skill-creator 官方元技能：帮你创建、优化、打包 Skill，自带测试评估工具

特别推荐 skill-creator 这个「元技能」：它的工作流是明确需求 → 起草 SKILL.md → 设计测试用例 → 有无 Skill 对比测试 → 评估打分 → 修改 → 打包的循环迭代。你甚至可以直接对 Agent 说「把我刚才教你的 Docker 配置逻辑总结成一个 Skill」，它会自动生成文件。

⚠️ 经验之谈：需求阶段就把细节和边界情况说清楚 —— 后期测试踩的坑，大多源于需求阶段的模糊。

全文总结

Skills 的本质，是把人类的领域知识、工作流程和最佳实践，封装成 AI 可复用的能力单元。SKILL.md = YAML 元数据（告诉 AI「我是谁、何时用我」）+ Markdown 指令（告诉 AI「具体怎么做」）。

写好一个 Skill 的心法只有三条：description 当触发器来写，指令当 SOP 来写，脚本当给新同事的 CLI 工具来写。剩下的，交给渐进式披露和调试三板斧。
