MySQL 的间隙锁（Gap Lock）是 InnoDB 存储引擎在可重复读（Repeatable Read, RR）隔离级别下，为了解决幻读（Phantom Read）问题而引入的一种特殊锁机制。

以下是关于间隙锁的详细介绍：

什么是间隙锁？

间隙锁是一种加在索引记录之间的间隙上的锁，而不是加在记录本身上。它的主要目的是阻止其他事务在该间隙中插入新的记录。

  • 锁定范围： 锁定的是两个索引值之间的“开区间”或“半开半闭区间”。

  • 不锁记录本身： 间隙锁只禁止插入，不禁止更新或删除已有的记录。

  • 兼容性： 间隙锁之间是兼容的（即多个事务可以同时持有同一间隙的间隙锁），但间隙锁与插入意向锁（Insert Intention Lock） 是冲突的。

为什么需要间隙锁？

在 RR 隔离级别下，MySQL 需要保证同一个事务内多次执行相同的范围查询，结果集是一致的。如果没有间隙锁：

场景： 事务 A 查询 SELECT * FROM t WHERE id > 5 FOR UPDATE;

问题： 如果此时事务 B 插入了 id=6 的记录并提交，事务 A 再次执行相同查询时就会看到新记录，这就产生了幻读。

解决： 间隙锁会锁住 (5, +∞) 这个范围，阻止事务 B 插入 id=6，从而避免幻读。

间隙锁的代码解读

DB::transaction(function () use ($roomId, $number, $date, $dateType, $type) {
    if (!DataStatistic::query()->where(['room_id' => $roomId, 'date_type' => $dateType, 'date' => $date])
        ->increment('value', $number)) {
        DataStatistic::query()->firstOrCreate([
            'room_id' => $roomId,
            'date_type' => $dateType,
            'date' => $date,
        ], ['value' => $number]);
    }
});

如上代码在高并发运行时极易产生死锁，解读如下：

死锁原因分析

核心问题在于：事务内 increment(UPDATE) → firstOrCreate(SELECT + INSERT) 的加锁顺序冲突。

死锁复现（行不存在时）

假设两个并发事务操作同一组 (room_id, date_type, date)，且该行尚不存在：

死锁场景（行不存在时，REPEATABLE READ 隔离级别）：

时间 事务 A 事务 B
T1 increment → UPDATE 扫描，0行，在唯一索引 gap 上留下 X gap lock
T2 increment → UPDATE 扫描，0行，在唯一索引 gap 上留下 X gap lock
T3 first() → 普通 SELECT，快照读，无锁，返回 null
T4 first() → 普通 SELECT，快照读，无锁，返回 null
T5 INSERT → 插入需要 X 锁，被 B 的 gap X 锁阻塞
T6 INSERT → 插入需要 X 锁，被 A 的 gap X 锁阻塞
T7 DEADLOCK

关键点：在 REPEATABLE READ 下，increment 的 UPDATE 虽然没更新到行，但扫描过程中会在唯一索引的 gap 上产生 X 锁（gap lock）。两个事务各持有一个 gap X 锁，然后都要 INSERT 到同一个 gap 中，INSERT 需要 insert intention gap lock，而 insert intention lock 与对方的 X gap lock 互斥 → 互相等待 → 死锁。

如果行已存在

行已存在时死锁风险较低（increment 直接成功，走单行 X 锁），但如果在同一个事务中有其他表/其他行的操作，UPDATE 的行锁与后续 INSERT 的 gap lock 也可能交叉死锁。

根本原因总结

  1. increment 的 UPDATE 在 REPEATABLE READ 下产生 gap lock
  2. firstOrCreate 的 SELECT 也产生 gap lock（S 锁）
  3. INSERT 需要 X 锁，与对方的 S gap lock 冲突
  4. 事务将多个操作捆绑，放大了锁的持有时间和冲突面

解决思路

# 方案 1： SELECT FOR UPDATE + 条件分支
DB::transaction(function () use ($roomId, $type, $number, $dateType, $date) {
        $row = VideoLiveDataStatistic::query()
            ->where(['room_id' => $roomId, 'date_type' => $dateType, 'date' => $date])
            ->lockForUpdate()
            ->first();

        if ($row) {
            $row->increment('value', $number);
        } else {
            VideoLiveDataStatistic::query()->create([
                'room_id' => $roomId,
                'date_type' => $dateType,
                'date' => $date,
                'value' => $number,
            ]);
        }
    });

# 在 DB::transaction + lockForUpdate() 的保护下，这段代码是安全的。但前提是：你的数据库隔离级别必须是默认的 REPEATABLE READ（MySQL InnoDB 默认值）。
# 🔍 为什么不会重复插入？
# 当 lockForUpdate() 查询不到数据时，InnoDB 并不会"什么都不锁"，而是会对该查询条件对应的索引间隙（Gap）加排他锁：
# 事务 A 执行 SELECT ... WHERE room_id=1 AND date_type='day' AND date='2026-07-08' FOR UPDATE → 未找到行 → 对该组合的间隙加 X 锁。
# 事务 B 执行相同查询 → 被间隙锁阻塞，等待事务 A 提交或回滚。
# 事务 A 执行 INSERT → 成功 → 提交 → 释放间隙锁。
# 事务 B 获得锁 → 再次执行 SELECT ... FOR UPDATE → 此时能查到事务 A 刚插入的行 → 走 increment 分支。
# ⚠️ 关键前提：这依赖于 InnoDB 在 REPEATABLE READ 隔离级别下的 Next-Key Lock / Gap Lock 机制。
# 如果隔离级别被改为 READ COMMITTED，间隙锁不存在，两个并发事务都可能查到空结果并各自插入，就会产生重复数据。

# 方案2：upsert , 但这个方案会导致 自增跳号问题，有自增  ID 的不建议使用

 DB::transaction(function () use ($roomId, $number, $dateType, $date) {
        VideoLiveDataStatistic::query()->upsert(
            [
                ['room_id' => $roomId, 'date_type' => $dateType, 'date' => $date, 'value' => $number] 
            ],
            ['room_id', 'date_type', 'date', 'type'], // 要保证唯一索引
            ['value' => DB::raw("`value` + $number")]
        );
    });

对比原代码

原代码 本方案
加锁顺序 UPDATE(隐式gap lock) → SELECT(无锁) → INSERT SELECT FOR UPDATE(显式行锁) → INSERT/UPDATE
死锁风险 有（gap lock 交叉） 无（锁顺序一致）
自增 ID 消耗 正常 正常（只有真正 INSERT 才消耗）
事务安全 有 有

Next-Key Lock（临键锁）

在实际实现中，InnoDB 很少单独使用纯粹的间隙锁，而是将其与记录锁组合成 Next-Key Lock（临键锁）。

Next-Key Lock = Record Lock（记录锁）+ Gap Lock（间隙锁）

  • 定义： 锁定一个左开右闭区间 (a, b]。

  • 作用： 既锁定了记录 b 本身（防止被修改/删除），也锁定了记录 b 前面的间隙（防止在 a 和 b 之间插入新记录）。

  • 默认行为： 在 RR 级别下进行范围查询或唯一性检查失败时，InnoDB 默认加的就是 Next-Key Lock。

加锁规则总结（RR 级别）

访问类型 加锁情况 说明
唯一索引 + 等值查询 + 记录存在 Record Lock 仅锁记录本身，退化为记录锁
唯一索引 + 等值查询 + 记录不存在 Gap Lock / Next-Key Lock 锁定该记录应该存在的间隙，防止插入
唯一索引 + 范围查询 Next-Key Lock 锁定扫描到的每个记录及其前面的间隙
非唯一索引 + 等值查询 Next-Key Lock + Gap Lock 锁住匹配记录的 Next-Key Lock，并向右锁定下一个区间的 Gap Lock（防止从右侧插入重复值）
无索引 / 全表扫描 Next-Key Lock (所有) 锁住整张表的所有记录和间隙（性能极差）

间隙锁带来的副作用

虽然间隙锁解决了幻读，但也带来了一些负面影响：

  1. 死锁风险增加： 因为间隙锁之间互相兼容，两个事务可能同时持有同一间隙的 S-Gap Lock，当它们都试图插入时，都需要获取 X-Insert Intention Lock，从而导致死锁。

  2. 并发插入性能下降： 即使插入的数据互不影响，只要落在同一个被锁定的间隙内，就会被阻塞。

  3. 主从复制问题： 在 Statement 格式的二进制日志下，间隙锁可能导致从库回放时产生不一致（MySQL 5.7+ 引入了 innodb_locks_unsafe_for_binlog 等参数来缓解）。

如何规避间隙锁的问题？

  • 降低隔离级别至 RC（Read Committed）： 在 RC 级别下，InnoDB 不会产生间隙锁（除了外键约束检查），只有 Record Lock。这是解决间隙锁死锁和并发插入问题最直接的方法。

  • 优化 SQL： 尽量走唯一索引的等值查询，避免范围查询和非唯一索引查询。

  • 合理设计索引： 减少不必要的辅助索引，避免非唯一索引等值查询时产生的额外间隙锁。

  • 业务层面控制： 对于批量插入操作，可以考虑合并事务或使用 LOAD DATA 等方式减少锁竞争。

💡 核心记忆点

间隙锁 = RR 级别的产物 + 防幻读的利器 + 死锁的常见元凶。

如果你的业务对幻读不敏感，或者频繁遇到间隙锁导致的死锁/性能问题，请优先考虑将隔离级别调整为 Read Committed。
