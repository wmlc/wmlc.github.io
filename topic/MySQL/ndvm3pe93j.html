一次锁冲突并不等于死锁。对 InnoDB 来说，大多数普通的行锁冲突首先表现为等待；只有等不到锁、发生死锁等情况，才会以异常结束。真正容易踩坑的，是“锁等待超时之后，事务到底回滚了多少”。

TL;DR

先记住 5 件事：

  1. InnoDB 中，遇到不兼容的行锁时，默认是等待，不是立即失败。
  2. innodb_lock_wait_timeout 默认是 50 秒；超时通常返回 ERROR 1205。
  3. 锁等待超时默认只回滚当前语句，不会自动回滚整个事务。
  4. 死锁是另一条路径：InnoDB 会主动检测，通常返回 ERROR 1213，并回滚被选中的整个事务。
  5. 在 Laravel 中，DB::transaction() 会在事务闭包抛出异常时回滚整个事务；但如果你在闭包内部把 1205 异常吞掉，Laravel 就会认为闭包正常结束，从而可能提交剩余修改。

一、MySQL 行锁冲突：默认是等待

假设事务 A 已经锁住 id = 1：

-- 事务 A
BEGIN;

SELECT *
FROM users
WHERE id = 1
FOR UPDATE;

此时事务 A 持有该行的排他锁。

事务 B 再修改同一行：

-- 事务 B
BEGIN;

UPDATE users
SET name = 'Tom'
WHERE id = 1;

如果这个锁与事务 A 持有的锁不兼容，B 不会立即失败，而是进入 LOCK WAIT。

可以把过程理解成：

事务 A                         事务 B
  │                              │
  │ SELECT ... FOR UPDATE        │
  │────── 获得 X 锁 ────────────>│
  │                              │
  │                         UPDATE id=1
  │                              │
  │                         ⏳ 等待锁
  │                              │
  │ COMMIT                       │
  │────── 释放锁 ───────────────>│
  │                              │
  │                         ✅ 获得锁
  │                         继续执行

如果阻塞事务一直不释放锁，等待时间超过 innodb_lock_wait_timeout，才会返回：

ERROR 1205 (HY000):
Lock wait timeout exceeded; try restarting transaction

MySQL 8.0 官方文档明确说明，innodb_lock_wait_timeout 默认值为 50 秒，并且这个参数控制 InnoDB 事务等待行锁的时间。

二、锁等待和死锁，不是一回事

这两个问题经常被混在一起。

对比 锁等待超时 死锁
错误码 1205 1213
本质 一方等待另一方释放锁 多个事务形成环形等待
检测方式 等到 timeout InnoDB 主动检测
默认等待 50 秒 是 否
回滚范围 默认当前语句 被选中的整个事务
是否应该重试 视业务情况 通常可以考虑

例如：

事务 A 持有锁 1
事务 B 请求锁 1

A 不等待 B
B 等待 A

这只是普通锁等待。

而：

事务 A 持有锁 1
事务 B 持有锁 2

A 请求锁 2
B 请求锁 1

就形成了：

A → 等 B
B → 等 A

这是死锁。

因此：

锁等待超时不等于死锁。

没有形成环形等待时，通常就是等待；等不到才返回 1205。

三、最容易忽略的地方：1205 默认只回滚当前语句

这是整篇文章最值得记住的一点。

查看参数：

SHOW VARIABLES LIKE 'innodb_rollback_on_timeout';

默认通常是：

OFF

当锁等待超时发生时：

innodb_rollback_on_timeout = OFF
        │
        ▼
当前语句回滚
        │
        ├── 前面的语句：仍然保留在当前事务中
        ├── 当前超时语句：回滚
        └── 事务：仍然存在

MySQL 官方文档明确说明：默认情况下，锁等待超时只回滚最后一条语句；如果启用 innodb_rollback_on_timeout，才会回滚整个事务。

四、为什么这会造成业务逻辑问题？

看一个转账例子：

BEGIN;

UPDATE account
SET balance = balance - 100
WHERE user = 'A';

UPDATE account
SET balance = balance + 100
WHERE user = 'B';

假设第二条 UPDATE 因为 B 的账户被其他事务锁住，等待 50 秒后发生 1205。

在默认配置下，结果是：

A 扣款 100       ✅ 保留在当前事务
B 加款 100       ❌ 当前语句回滚
事务本身         🟡 仍然存在

此时千万不要把“当前语句回滚”理解成“整个转账失败并且事务已经回滚”。

实际上：

数据库状态：

A：-100  ← 仍在当前事务中
B：  0   ← 第二条语句没有生效

如果应用随后错误地继续执行并最终 COMMIT，就可能出现：

A 扣了 100
B 没收到 100

这就是 innodb_rollback_on_timeout=OFF 最危险的地方。

五、“本事务能看到前面的修改”不叫脏读

还有一个容易写错的概念。

例如：

BEGIN;

UPDATE orders
SET status = 'paid'
WHERE id = 1;

SELECT status
FROM orders
WHERE id = 1;

当前事务通常可以看到自己刚刚修改的数据。

这不能称为“脏读”。

脏读（Dirty Read）指的是一个事务读取到了另一个尚未提交事务的数据。

这里读取的是：

当前事务自己的未提交修改。

所以更准确的说法应该是：

当前事务可以看到自己的未提交修改

而不是：

发生了脏读

六、innodb_rollback_on_timeout=ON 是不是更安全？

如果你的业务希望：

只要事务中的某条 SQL 因锁等待超时失败，就把整个事务作为一个整体失败。

那么可以考虑：

[mysqld]
innodb_rollback_on_timeout = ON

此时：

stmt1 ✅
stmt2 ❌ 1205
   │
   ▼
整个事务回滚
   │
   ├── stmt1 回滚
   └── stmt2 回滚

这个行为对于强事务一致性的业务更加直观。

需要注意的是，innodb_rollback_on_timeout 是启动时配置项，不是动态变量。因此修改后通常需要重启 MySQL。

不过我不建议把它理解成：

“打开 ON，以后应用层就不用处理事务异常了。”

应用层仍然应该正确处理异常，并在事务边界上保证业务原子性。

七、Laravel 会不会处理这个问题？

如果使用 Laravel 的：

DB::transaction(function () {
    // ...
});

情况会好很多。

Laravel 官方文档明确说明：

如果事务闭包抛出异常，Laravel 会自动回滚事务，并重新抛出异常；如果闭包正常执行结束，则自动提交。

例如：

DB::transaction(function () {
    DB::table('account')
        ->where('user', 'A')
        ->decrement('balance', 100);

    DB::table('account')
        ->where('user', 'B')
        ->increment('balance', 100);
});

假设第二条 SQL 发生 1205：

MySQL
  │
  ├── 第二条语句失败
  │
  ▼
Laravel 收到异常
  │
  ▼
DB::transaction() 回滚整个事务
  │
  ├── A 的扣款回滚
  └── B 的加款没有生效

因此：

MySQL 默认只回滚当前语句，并不意味着 Laravel 的 DB::transaction() 也只回滚当前语句。

这是两个不同层面的行为。

MySQL 决定“这条 SQL 超时之后数据库层面怎么处理”。

Laravel 的事务封装则在异常继续向上传播时负责回滚整个 Laravel 事务。

八、真正危险的是：把异常吞掉

例如：

DB::transaction(function () {
    DB::table('account')
        ->where('user', 'A')
        ->decrement('balance', 100);

    try {
        DB::table('account')
            ->where('user', 'B')
            ->increment('balance', 100);
    } catch (\Throwable $e) {
        Log::warning('B 加钱失败');
        // ❌ 异常被吃掉
    }

    DB::table('transfer_log')->insert([
        'status' => 'completed',
    ]);
});

从 Laravel 的角度看：

闭包执行完毕
    ↓
没有异常向外抛
    ↓
认为事务成功
    ↓
COMMIT

于是就可能得到：

A 扣款       ✅
B 加款       ❌
transfer_log completed  ✅

所以真正应该强调的是：

Laravel 能兜住“异常正常抛出”的事务失败，但不能替你判断一个被 catch 后吞掉的异常是否意味着业务应该回滚。

如果必须捕获异常，通常应该：

DB::transaction(function () {
    DB::table('account')
        ->where('user', 'A')
        ->decrement('balance', 100);

    try {
        DB::table('account')
            ->where('user', 'B')
            ->increment('balance', 100);
    } catch (\Throwable $e) {
        Log::error('转账失败', [
            'exception' => $e,
        ]);

        throw $e;
    }
});

九、Laravel 会自动重试 1205 吗？

这里也很容易产生误解。

Laravel 的：

DB::transaction($callback, $attempts);

第二个参数主要用于死锁重试。

例如：

DB::transaction(function () {
    // ...
}, 5);

Laravel 官方文档把这个参数定义为：

当发生死锁时，事务可以重新尝试执行。

因此不要简单地写成：

1205 和 1213 都自动重试

更准确的说法是：

1213 / 死锁
    → Laravel 的 transaction attempts 可以自动重试

1205 / 锁等待超时
    → 不应把 attempts 当成 1205 的通用自动重试机制

如果业务确实需要对 1205 做重试，可以在事务外层自己封装：

function transactionWithRetry( Closure $callback, int $attempts = 3 ): mixed {
    for ($i = 1; $i <= $attempts; $i++) {
        try {
            return DB::transaction($callback);
        } catch (\Illuminate\Database\QueryException $e) {
            $code = $e->errorInfo[1] ?? null;

            if (!in_array($code, [1205, 1213], true) || $i === $attempts) {
                throw $e;
            }

            usleep($i * 100_000);
        }
    }

    throw new RuntimeException('Transaction retry failed.');
}

这里有一个非常重要的原则：

重试应该重试整个事务，而不是从失败的那条 SQL 继续执行。

因为事务前面的 SQL 可能已经执行过。

十、为什么不能只重试失败的 SQL？

还是转账：

stmt1：A -100   ✅
stmt2：B +100   ❌ 1205

如果只重新执行 stmt2：

A -100
B +100

看起来似乎没问题。

但如果你的代码结构更复杂：

stmt1
stmt2
stmt3
stmt4

而 stmt3、stmt4 又依赖前面的状态，简单从失败点继续执行很容易破坏业务语义。

更危险的是，如果你把整个业务循环重新执行，却没有 rollback：

第一次：
A -100
B +100  ← 失败

第二次：
A -100  ← 又执行一次
B +100

就可能变成：

A -200
B +100

所以正确的重试模型应该是：

BEGIN
  ↓
执行整个业务
  ↓
失败
  ↓
ROLLBACK
  ↓
重新 BEGIN
  ↓
重新执行整个业务
  ↓
COMMIT

十一、手动事务时，责任就回到开发者身上

例如：

DB::beginTransaction();

try {
    DB::table('account')
        ->where('user', 'A')
        ->decrement('balance', 100);

    DB::table('account')
        ->where('user', 'B')
        ->increment('balance', 100);

    DB::commit();
} catch (\Throwable $e) {
    DB::rollBack();

    throw $e;
}

这里的原则非常简单：

事务开始之后，只要业务没有成功完成，就必须确保最终执行 rollback。

Laravel 并不会因为你调用了：

DB::beginTransaction();

就自动替你补上一个可靠的异常处理结构。

因此在 Laravel 项目中，我更倾向于：

DB::transaction(function () {
    // 业务逻辑
});

而不是到处手写：

beginTransaction();
try {
    ...
    commit();
} catch (...) {
    rollBack();
}

十二、锁等待监控：MySQL 8.0 不要再使用旧表

原文中有一处需要特别修正。

MySQL 8.0 应该使用：

performance_schema.data_locks
performance_schema.data_lock_waits

而不是：

information_schema.INNODB_LOCKS
information_schema.INNODB_LOCK_WAITS

后两者属于旧版本的锁信息表，在 MySQL 8.0 已被 Performance Schema 对应表取代。

例如：

SELECT *
FROM performance_schema.data_lock_waits;

可以看到哪些锁请求正在被哪些锁阻塞。

如果希望进一步查看锁的具体对象，可以关联：

performance_schema.data_locks

以及：

information_schema.INNODB_TRX

生产环境排查锁等待时，建议优先使用 MySQL 8.0 官方推荐的数据源，而不要直接复制网上基于 MySQL 5.7 的 SQL。

十三、Laravel 的悲观锁应该怎么用？

Laravel 本身提供了：

->lockForUpdate()

以及：

->sharedLock()

例如：

DB::transaction(function () {
    $account = DB::table('account')
        ->where('user', 'A')
        ->lockForUpdate()
        ->first();

    // 修改 account
});

这里的关键不是：

“用了 lockForUpdate() 就不会死锁。”

而是：

锁的顺序、事务边界、锁持有时间，才是并发事务设计的核心。

例如两个事务：

事务 A：
锁 account 1
锁 account 2

事务 B：
锁 account 2
锁 account 1

就可能产生：

A 持有 1，等待 2
B 持有 2，等待 1

形成死锁。

因此对于需要同时操作多行的业务，一个非常重要的设计原则是：

尽量让所有事务按照统一顺序获取锁。

例如按照主键升序：

1 → 2 → 3 → 4

而不是：

事务 A：1 → 2 → 3
事务 B：3 → 2 → 1

十四、我更推荐的事务设计原则

结合实际业务开发，我会把 MySQL 锁问题归纳成下面几条。

1. 事务尽可能短

不要在事务中：

请求外部 HTTP API
调用第三方服务
等待用户操作
执行大量复杂计算
sleep

因为事务越长：

锁持有时间越长
    ↓
其他事务等待时间越长
    ↓
1205 概率上升
    ↓
并发冲突更加严重

2. 多行更新尽量统一锁顺序

例如统一：

按 id 升序加锁

可以显著降低因为锁顺序不一致导致的死锁概率。

3. 1205 和 1213 分开处理

不要简单地：

catch (Throwable $e) {
    retry();
}

至少应该区分：

1205：锁等待超时
1213：死锁

两者产生原因不同。

4. 重试一定是整个事务

错误方式：

失败 SQL → 直接重试 SQL

更可靠的方式：

整个事务 rollback
        ↓
重新开启事务
        ↓
完整执行整个业务

5. Laravel 优先使用 DB::transaction()

DB::transaction(function () {
    // 所有事务业务
});

让框架处理：

BEGIN
  ↓
业务代码
  ↓
异常？
 ├─ 是 → ROLLBACK
 └─ 否 → COMMIT

6. 不要在事务闭包里吞掉异常

尤其是：

try {
    // 数据库操作
} catch (\Throwable $e) {
    Log::error($e);
    // 什么都不做
}

这相当于告诉 Laravel：

“没事，继续提交吧。”

如果业务上确实需要捕获并转换异常，要么重新抛出，要么明确执行回滚并结束事务。

十五、最终总结

MySQL 行锁冲突的实际过程，可以浓缩成：

请求锁
  │
  ▼
是否与已有锁冲突？
  │
  ├── 否 → 立即获得锁
  │
  └── 是
       │
       ▼
     进入等待
       │
       ├── 对方释放锁
       │      ↓
       │    获得锁，继续执行
       │
       └── 超过 innodb_lock_wait_timeout
              ↓
            ERROR 1205
              │
              ├── 默认 OFF
              │     → 当前语句回滚
              │     → 整个事务仍存在
              │
              └── ON
                    → 整个事务回滚

而死锁是另一条路径：

事务 A ──等待──> 事务 B
  ↑               │
  └────等待───────┘

        ↓

   InnoDB 检测到死锁

        ↓

   回滚其中一个事务

        ↓

      ERROR 1213

最后再看 Laravel：

DB::transaction()
      │
      ├── 正常结束 → COMMIT
      │
      └── 异常抛出 → ROLLBACK

所以真正值得记住的不是某一个参数，而是三个层次：

MySQL 层：
1205 默认只回滚当前语句

Laravel 事务层：
异常从 transaction 闭包抛出 → 整个事务 rollback

业务代码层：
如果你把异常吞掉，框架就可能认为事务成功

MySQL 的锁等待并不可怕，可怕的是应用程序没有正确理解“语句失败”和“事务失败”不是同一件事。

+
