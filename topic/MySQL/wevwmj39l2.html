死锁不是 bug，是并发设计的必然产物。理解它的成因，才能从根本上消灭它。

TL;DR

  • 死锁根源是加锁顺序不一致导致的环形等待。
  • 常规'排序后 UPDATE'会破坏有前后依赖的业务执行顺序，导致数据错误。
  • 预锁定方案：用 SELECT ... ORDER BY id FOR UPDATE 统一加锁顺序，再用原始顺序执行 UPDATE，从结构上彻底预防死锁。

一、死锁是怎么形成的

1.1 死锁的四个必要条件

数据库死锁本质上和操作系统死锁一样，必须同时满足四个条件：

条件 含义 在 MySQL 中的表现
互斥 资源同一时刻只能被一个事务持有 行锁是排他的
持有并等待 持有锁的同时请求新锁 事务持锁期间继续 UPDATE
不可抢占 已持有的锁不能被强制剥夺 只有事务提交/回滚才释放
环形等待 存在循环依赖链 A 等 B，B 又等 A

打破任何一个条件，死锁就不可能发生。 预锁定方案打破的是第四个——环形等待。

1.2 一个真实的死锁现场

两个事务更新同一张表，业务顺序不同：

事务A 业务顺序：id = 1 → 7 → 8 → 2
事务B 业务顺序：id = 2 → 7 → 8 → 4

交集：id = 2, 7, 8

按各自业务顺序逐条 UPDATE ... WHERE id = ?：

时刻1: 事务A 执行 UPDATE WHERE id=1  → 持有锁{1}
时刻2: 事务B 执行 UPDATE WHERE id=2  → 持有锁{2}
时刻3: 事务A 执行 UPDATE WHERE id=7  → 持有锁{1,7}
时刻4: 事务B 执行 UPDATE WHERE id=7  → ⏳ 阻塞，等事务A释放7
时刻5: 事务A 执行 UPDATE WHERE id=8  → 持有锁{1,7,8}
时刻6: 事务A 执行 UPDATE WHERE id=2  → ⏳ 阻塞，等事务B释放2

死锁形成：

事务A: 持有 {1,7,8}，等待 2（被B持有）
事务B: 持有 {2}，    等待 7（被A持有）

A → 等B → B → 等A → 环！

MySQL 的 InnoDB 死锁检测器（wait-for graph）发现环后，会回滚代价较小的事务，并抛出 ERROR 1213 (Deadlock found)。

1.3 死锁的根源：加锁顺序不一致

把上面的过程抽象成加锁序列：

事务A 加锁顺序：1 → 7 → 8 → 2
事务B 加锁顺序：2 → 7 → 8 → 4

两个事务对交集资源 {7, 8, 2} 的加锁顺序不同：

  • A 先锁 7 再锁 2
  • B 先锁 2 再锁 7

只要存在两个事务对同一组资源以不同顺序加锁，就存在死锁的可能性。

二、死锁预防 vs 死锁检测 vs 死锁避免

策略 做法 优缺点
死锁检测 InnoDB 默认行为，检测到环后回滚一个事务 事后补救，有性能开销，业务需处理重试
死锁避免 谨慎安排加锁顺序，尽量降低概率 不彻底，只是降低概率
死锁预防 从结构上保证不可能形成环 彻底消除，本文方案

预锁定方案属于死锁预防——从结构上保证环形等待不可能出现。

三、为什么"排序后逐条 UPDATE"不够

最直觉的防死锁手段：所有事务按相同顺序加锁。

事务A 排序后：1 → 2 → 7 → 8
事务B 排序后：2 → 4 → 7 → 8

方向一致了，死锁确实不会发生。但问题是：

业务顺序被破坏了。

如果业务逻辑是：

  1. 先更新 id=1，计算出中间值 X
  2. 用 X 更新 id=7
  3. 用 id=7 的结果更新 id=8
  4. 最后用 id=8 的结果更新 id=2

强行改成 1→2→7→8 会导致步骤 4 拿不到步骤 3 的结果，数据错误。

我需要：加锁顺序统一，但执行顺序不变。

四、预锁定方案：解耦加锁与执行

核心思想

┌──────────────────────────────────────────────────────┐
│                                                      │
│   第一步：预锁定（加锁阶段）                          │
│   ─────────────────────                              │
│   SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE│
│   → 按 id 升序，一次性拿齐所有 X 锁                  │
│   → 加锁顺序：全局统一（id 升序）                    │
│                                                      │
│   第二步：业务执行（计算阶段）                        │
│   ─────────────────────                              │
│   按原始业务顺序逐条 UPDATE                           │
│   → 锁已全部持有，不会再产生新的锁等待               │
│   → 执行顺序：完全由业务决定                         │
│                                                      │
│   加锁顺序归数据库，执行顺序归业务。                  │
│                                                      │
└──────────────────────────────────────────────────────┘

为什么这能打破环形等待？

死锁要求'持有并等待'形成环。预锁定之后：

  • 业务执行阶段不再产生任何新的锁请求（锁已经全部持有）
  • 没有新的锁请求 → 没有新的等待 → 不可能形成新的依赖边
  • 唯一可能产生等待的地方是预锁定阶段
  • 而预锁定阶段所有事务的加锁方向一致（id 升序）→ 不可能成环

环形等待被从两个维度同时封死。

五、深入：IN (...) 是逐个加锁的，为什么还是安全的？

5.1 InnoDB 的实际执行过程

SELECT * FROM your_table WHERE id IN (1,2,7,8) ORDER BY id ASC FOR UPDATE;

InnoDB 内部：

  1. 优化器将 IN 列表排序为 [1, 2, 7, 8]
  2. 沿聚簇索引从 id=1 开始扫描
  3. 定位到 id=1 → 立即加 X 锁 → 继续
  4. 定位到 id=2 → 立即加 X 锁 → 继续
  5. ... 直到全部完成
  6. 返回结果集

锁是逐条、逐步获取的，不是一条 SQL 执行完才统一加锁。

5.2 逐步加锁会不会产生交叉等待？

会。但只是单向阻塞，不会成环。逐帧推演：

事务A 预锁序列：[1, 2, 7, 8]
事务B 预锁序列：[2, 4, 7, 8]
时刻 事务 A 事务 B 持有锁 说明
T1 锁 id=1 ✅ — A:{1}
T2 尝试锁 id=2 ⏳ 锁 id=2 ✅ A:{1}, B:{2} A 被 B 阻塞
T3 ⏳ 阻塞中 锁 id=4 ✅ A:{1}, B:{2,4}
T4 ⏳ 阻塞中 锁 id=7 ✅ A:{1}, B:{2,4,7} B 不需要 id=1
T5 ⏳ 阻塞中 锁 id=8 ✅ A:{1}, B:{2,4,7,8} B 不需要 id=1
T6 ⏳ 阻塞中 业务执行 → COMMIT B 释放全部
T7 锁 id=2 ✅ → 7 ✅ → 8 ✅ — A:{1,2,7,8} A 解除阻塞
T8 业务执行 → COMMIT — 完成

关键：B 永远不会等 A。

为什么？因为：

  • A 在 T2 阻塞时，只持有 id=1
  • B 的预锁序列是 [2, 4, 7, 8]，最小是 2
  • B 需要的所有 id 都 > 1
  • B 永远不会去请求 id=1 → B 永远不会等 A

依赖只有 A→B 一个方向，没有环。

5.3 数学证明：全序关系消除环形等待

全序关系消除死锁的数学证明

**定理**：若所有事务对资源集合 S 按相同的全序关系 < 获取锁，则不会发生死锁。

**证明**（反证法）：

假设存在死锁，则存在环形等待：

$$T_1 \xrightarrow{\text{等待}} T_2 \xrightarrow{\text{等待}} \cdots \xrightarrow{\text{等待}} T_1$$

设 $T_i$ 在等待资源 $r_i$，且 $r_i$ 被 $T_{i+1}$ 持有。

由于所有事务按升序加锁：
- $T_i$ 在等待 $r_i$ 时，$T_i$ 已持有的所有锁 < $r_i$
- $T_{i+1}$ 持有 $r_i$，说明 $T_{i+1}$ 已获取到 $r_i$
- $T_{i+1}$ 后续要获取的锁都 ≥ $r_i$

因此 $T_{i+1}$ 不可能等待 $T_i$ 持有的锁（那些锁 < $r_i$ ≤ $T_{i+1}$ 当前进度）。

这与环形等待矛盾。∎

**直觉理解**：所有人从左往右拿东西，左边的人等右边的人，但右边的人永远不会回头看左边。没有回头，就没有环。

5.4 对比：乱序加锁为什么可能成环

事务A：锁1 → 锁7 → 锁2
事务B：锁2 → 锁7
T1: A 锁 1 ✅
T2: B 锁 2 ✅
T3: A 锁 7 ✅
T4: B 尝试锁 7 → ⏳ 等 A
T5: A 尝试锁 2 → ⏳ 等 B
→ 环！死锁！

乱序加锁时，'右边的人可能回头看左边'，环就可能出现。

六、RR 隔离级别下有间隙锁风险吗？

6.1 最初的担忧

REPEATABLE READ 下，FOR UPDATE 除了记录锁还可能加临键锁（Next-Key Lock）：

锁 id=2 → record lock(2) + next-key lock (1, 2] + gap lock (2, next)

如果预锁定加了间隙锁，两个事务的间隙锁可能重叠，产生隐式的交叉等待，破坏全序论证。

6.2 实测结论（MySQL 8.0）：主键等值查询不加间隙锁

MySQL 8.0 InnoDB 的明确规则：

For a unique index with a unique search condition, InnoDB locks only the index record found, not the gap before it.
— MySQL 8.0 Reference Manual, §15.7.1

实测验证：

-- id 为主键，IN 为等值条件
SELECT * FROM your_table WHERE id IN (1,2,7,8) ORDER BY id FOR UPDATE;

通过 SHOW ENGINE INNODB STATUS 或 performance_schema.data_locks 确认：

RECORD LOCKS space id ... index PRIMARY ... lock_mode X locks rec but not gap

只有 Record Lock，没有 Gap Lock，没有 Next-Key Lock。

6.3 结论

预锁条件 RR 下锁类型 是否有间隙锁风险
主键/唯一索引 + 等值 (IN / =) Record Lock only ❌ 安全
普通索引 + 等值 Record + Gap ⚠️ 有风险
范围查询 (BETWEEN / > / <) Next-Key Lock ⚠️ 有风险

主键预锁定方案在 RR 下直接可用，无需切换隔离级别。

如果预锁定无法走主键（比如先按 user_id 筛选），需要两步：

-- 第一步：查出 id（不加锁）
SELECT id FROM your_table WHERE user_id IN (...);

-- 第二步：用主键预锁
SELECT * FROM your_table WHERE id IN (2,4,7,8) ORDER BY id FOR UPDATE;

七、完整 SQL 实现

事务 A（业务顺序: 1 → 7 → 8 → 2）

BEGIN;

-- 预锁定：按 id 升序获取全部 X 锁
SELECT * FROM your_table
WHERE id IN (1, 2, 7, 8)
ORDER BY id ASC
FOR UPDATE;

-- 业务执行：原始顺序，锁已全部持有
UPDATE your_table SET col = compute_step1() WHERE id = 1;
UPDATE your_table SET col = compute_step2() WHERE id = 7;
UPDATE your_table SET col = compute_step3() WHERE id = 8;
UPDATE your_table SET col = compute_step4() WHERE id = 2;

COMMIT;

事务 B（业务顺序: 2 → 7 → 8 → 4）

BEGIN;

SELECT * FROM your_table
WHERE id IN (2, 4, 7, 8)
ORDER BY id ASC
FOR UPDATE;

UPDATE your_table SET col = compute_step1() WHERE id = 2;
UPDATE your_table SET col = compute_step2() WHERE id = 7;
UPDATE your_table SET col = compute_step3() WHERE id = 8;
UPDATE your_table SET col = compute_step4() WHERE id = 4;

COMMIT;

八、应用层代码（PHP / Laravel）

function batchUpdateWithBusinessOrder(array $businessOrderIds): void
{
    DB::transaction(function () use ($businessOrderIds) {
        // ① 预锁定：按 id 升序
        $sortedIds = $businessOrderIds;
        sort($sortedIds);

        $placeholders = implode(',', array_fill(0, count($sortedIds), '?'));
        DB::select(
            "SELECT * FROM your_table WHERE id IN ({$placeholders}) ORDER BY id ASC FOR UPDATE",
            $sortedIds
        );

        // ② 按原始业务顺序执行
        foreach ($businessOrderIds as $id) {
            // 根据业务计算新值
            $newValues = ['col' => compute_value_for_id($id)];
            DB::table('your_table')->where('id', $id)->update($newValues);
        }
    });
}

九、注意事项

# 要点 说明
1 预锁必须走主键/唯一索引 否则加锁顺序不可控，全序论证不成立
2 所有并发事务用相同排序方向 统一 ASC，不能混用
3 主键等值 + RR 即可 无需切换 RC（MySQL 8.0 实测）
4 重试机制保留 作为极端场景兜底
5 预锁结果复用 避免业务阶段重复 SELECT
6 事务尽量短 持锁时间越长，阻塞窗口越大
7 IN 列表不宜过长 过长拉长预锁阶段，增加阻塞概率
8 警惕热点行阻塞 若 IN 列表含高频访问 id，预锁阶段可能造成大面积阻塞，需评估业务容忍度

十、方案对比

方案 防死锁机制 保持业务顺序 并发度 适用场景
不处理，靠重试 死锁检测（事后） ✅ 🟢 高 低冲突场景
排序后逐条 UPDATE 全序（但破坏业务） ❌ 🟢 中高 无前后依赖
合并 CASE WHEN 单语句内引擎控制 ❌ 🟢 高 可统一表达
预锁定 + 原序执行 全序（预防） ✅ 🟢 中高 业务顺序不可变
全局串行锁 消除并发 ✅ 🔴 串行 极低频

十一、总结

死锁的本质是环形等待。

预锁定方案的本质是：

用一条 SELECT ... ORDER BY id FOR UPDATE 把加锁收敛到一个方向确定的阶段，让业务执行阶段不再产生任何新的锁请求。加锁有全序，执行无等待，环无从形成。

加锁顺序 → 归数据库（id 升序，全局统一，全序无环）
执行顺序 → 归业务（1→7→8→2，完全不变）
两者解耦，死锁消亡。

一句话总结：预锁定方案的本质，是把'怎么拿锁'的控制权交给数据库（全序），把'怎么干活'的控制权留给业务（原序），二者解耦，死锁消亡。

测试环境：MySQL 8.0，InnoDB，REPEATABLE READ
